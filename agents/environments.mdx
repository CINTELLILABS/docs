An agent exists in three places at once. You edit one of them. The other two hold whatever you last shipped there, which on a new agent is nothing.

**Development** is the agent you are working on, saved work and unsaved alike. **Staging** and **Production** are snapshots: each one pins a single version and holds it until you move it. You cannot edit staging or production, only point them at something else.

## Prerequisites

- An agent you have built, from [Agent builder](/agents/agent-builder)
- An owner, admin, operator or prompter role. A viewer can see the Environments tab but cannot publish, promote, roll back or save a variable
- Optional: evaluations configured on staging, if you want them to gate the publish into staging and the promotion out of it. See [Evaluations](/agents/evaluations)

## Where environments live

Inside an agent, **Environments** is under **Configure**. It has two tabs, **Environments** and **Variables**.

There is no organization-wide view. Environments belong to one agent, and you reach them from that agent.

{/* IMAGE: the Environments tab inside an agent, showing the Production, Staging and Development cards. */}

Staging and production each show the **Version** they are pinned to and when it arrived, **Deployed** on production and **Created** on staging. Development shows neither, because it is the live head rather than a pin. An environment holding nothing shows no version and no buttons at all.

<Warning>
A call runs the **production** version by default. An agent with nothing pinned to production has nothing to serve, and an API call is refused with a 400 and the code `AGENT_ENV_UNPINNED`.

Building and saving is not shipping.
</Warning>

## Your first publish goes straight to production

A new agent is in this state. Until production holds a version, the Environments tab offers one move instead of two.

The Staging card and the **Evaluations** card that reports on it are both greyed out, and the staging card explains why: *"Not in use until Production has a version. Publish sends Development straight to Production."* The Development card carries a single **Publish** that releases development **directly to production**.

There is no staging hop to make, which is the point: staging cannot usefully hold anything before production has a baseline to compare against.

Once production is pinned, the Environments tab switches to the two-step flow and stays there.

## Publish to staging

Once production holds a version, **Publish** on the Development card takes your current work, saves it as a new version, and pins that version to staging. Publishing to staging does not move production, so callers keep getting the version production already holds.

## Promote to production

**Promote** on the Staging card points production at the version staging is holding. Nothing is copied and nothing is rebuilt.

Staging is the normal path but not the only one. **Force promote**, also on the Development card, releases a development version straight to production without the staging hop.

**Force promote** skips the evaluation gate as well as the staging hop. That is its purpose, and the bypass is recorded on the deployment. It is the control that puts unevaluated work in front of live callers.

## Roll back

To go back, **Rollback** on the Production card lists the versions production held before and repins to one you choose. It is a repoint, not a rebuild.

## The evaluation gate

Evaluations on staging can gate both moves, and the two directions fail differently.

With no evaluations configured, neither move is gated and both happen immediately. The same is true if you have configured them and marked none of them **Required**: a judge, the evaluation that scores a run, reports its verdict and never blocks when it is not required.

<Note>
One evaluation configuration does both jobs. The one saved on **staging** gates the publish into staging and the promotion out of it. There is no separate production gate to configure.
</Note>

Publishing to staging saves your changes as a new version, runs the evaluations against that exact version, and only assigns it a version number and pins it to staging once every required evaluation passes. A blocked publish says so, with a toast reading **Publish blocked** and the number of required evaluations that failed.

<Warning>
A blocked publish is not a rollback. The version is already saved on development, without a number and without a pin, and it stays there.

Nothing is undone and nothing is lost. Fix what failed and publish again.
</Warning>

Promotion is enforced on the server rather than in the dashboard, so a blocked promotion is refused outright: production keeps serving the version it already had, and nothing about staging changes.

A judge scores a rate, not a verdict per conversation. It passes when more than half of the scored conversations match the target, so a single bad conversation does not necessarily fail the run.

## Variables

The **Variables** tab holds keys and values that belong to an environment rather than to the agent. Pick **Development**, **Staging** or **Production** to choose which set you are editing.

The same key can carry a different value in development, staging and production. Reference one anywhere in the agent's configuration as `{"{{env.KEY}}"}`, and it resolves to the running environment's value when a call starts, which is how an agent points at a test system while it is on staging and a real one once it is promoted. A variable nothing references does nothing.

Marking a value **Secret** stores it in your secret vault and keeps only a reference here. It cannot be read back afterwards.

<Warning>
A key with no value in the environment the call is running in does not fall back to another environment. It fails the call before it starts, with `AGENT_VARIABLE_UNRESOLVED`.

So a variable added on development and never set on production breaks production the moment something references it.
</Warning>

## Common failures

<AccordionGroup>
  <Accordion title="The agent answers with old behavior">
    Production is pinned to an older version. Publishing to staging does not move production; check what production says it is pinned to, then **Promote**.
  </Accordion>

  <Accordion title="Calls fail and the agent looks fine in the builder">
    The agent has never reached production. The builder shows development, which is not what a call runs by default. On an API call the error is a 400 with `AGENT_ENV_UNPINNED`, which also names the alternative: pass `agent_version` to run a specific version deliberately.
  </Accordion>

  <Accordion title="Publish finished but staging did not move">
    A required evaluation failed, and the toast said so. The version is saved on development with no number and no pin, which is why nothing appears to have happened on staging.
  </Accordion>

  <Accordion title="Promotion is blocked although the evaluations passed">
    The configuration changed after that run. Promotion compares the run against the whole configuration saved now, which covers the required evaluations and the shared test inputs, so changing the scenarios or the conversation count invalidates a pass just as editing an evaluation does. Publish to staging again to run them against the current configuration.
  </Accordion>

  <Accordion title="A button does nothing and the error says nothing">
    Publishing, promoting, rolling back and saving a variable all need an owner, admin, operator or prompter role. The buttons are not disabled for a viewer, so the press fails with a generic message rather than telling you the cause.
  </Accordion>

  <Accordion title="A variable is right in one place and wrong in another">
    Variables are per environment. Setting one on development leaves staging and production untouched, and promoting an agent does not carry values across.
  </Accordion>
</AccordionGroup>
