An agent exists in three places at once. You edit one of them and the other two carry versions you shipped earlier.

**Development** is the agent you are working on. **Staging** and **Production** are snapshots: each one pins a single version and holds it until you move it. You cannot edit staging or production, only point them at something else.

## Prerequisites

- An agent you have built, from [Agent builder](/agents/agent-builder)
- Evaluations configured on staging, if you want a gate between the two. Nothing requires one

## Where environments live

Inside an agent, **Environments** is under **Configure**. It has two tabs, **Environments** and **Variables**.

There is no organization-wide view. Environments belong to one agent, and you reach them from that agent.

## The three environments

| | What it holds | Who changes it |
|---|---|---|
| **Development** | Your unsaved and saved work. The only one you edit | You, in the builder |
| **Staging** | One pinned version, for testing | **Publish to staging** |
| **Production** | One pinned version, the one that takes real calls | **Promote** |

Each card shows the **Version** it is pinned to, and when it arrived: **Deployed** on production, **Created** on staging.

<Warning>
A call runs the **production** version. An agent that has never been promoted to production has nothing to answer with, and the call fails.

Building and saving is not shipping. Neither is publishing to staging.
</Warning>

## Publish to staging

**Publish to staging** takes your current development work and pins it to staging as a new version.

The version is written immediately, before anything is checked. What waits is the version *number*, the staging pin, and the deployment record.

## Promote to production

**Promote** moves the version currently on staging to production. Production then answers calls with it.

There is no way to promote development directly. Production only ever receives what staging is holding, so staging is the path rather than a suggestion.

To go back, **Roll back production** lists **Previous production versions** and repins to one you choose. It is a repoint, not a rebuild.

## The evaluation gate

If you have configured evaluations on staging, they gate the move between environments. This is the part worth reading twice, because the two directions behave differently.

Publishing to staging saves your changes as a new version, runs the evaluations against that exact version, and only assigns it a version number and pins it to staging once every required evaluation passes.

<Warning>
A blocked publish is not a rollback. The version is already saved on development, without a number and without a pin, and it stays there.

Nothing is undone and nothing is lost. Fix what failed and publish again.
</Warning>

Promotion to production is enforced differently, and more strictly: the server itself refuses it, in the same transaction that would have repointed production.

<Note>
One evaluation configuration does both jobs. The one saved on **staging** gates the publish into staging and the promotion out of it. There is no separate production gate to configure.
</Note>

Two things that surprise people:

- **Editing the configuration after a passing run blocks promotion again.** A run records the configuration it ran under, and promotion requires that record to match what is saved now. Changing the set of evaluations invalidates the pass.
- **A judge scores a rate, not a verdict per conversation.** It passes when enough of the scored conversations match the target, so a single bad conversation does not necessarily fail the run.

With no evaluations configured, neither move is gated and both happen immediately.

## Variables

The **Variables** tab holds keys and values that belong to an environment rather than to the agent.

The same key can carry a different value in development, staging and production, which is how an agent points at a test system while it is on staging and a real one once it is promoted. The **Environment** control picks which set you are editing.

## Common failures

<AccordionGroup>
  <Accordion title="The agent answers with old behavior">
    Production is pinned to an older version. Publishing to staging does not move production; check what production says it is pinned to, then **Promote**.
  </Accordion>

  <Accordion title="Calls fail and the agent looks fine in the builder">
    The agent has never reached production. The builder shows development, which never takes calls.
  </Accordion>

  <Accordion title="Publish finished but staging did not move">
    A required evaluation failed. The version is saved on development with no number and no pin, which is why nothing appears to have happened on staging.
  </Accordion>

  <Accordion title="Promotion is blocked although the evaluations passed">
    The configuration changed after that run. Promotion compares the run against the configuration saved now, so adding, removing or editing an evaluation invalidates an earlier pass. Run them again.
  </Accordion>

  <Accordion title="A variable is right in one place and wrong in another">
    Variables are per environment. Setting one on development leaves staging and production untouched, and promoting an agent does not carry values across.
  </Accordion>
</AccordionGroup>
