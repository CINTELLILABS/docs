The agent builder is where you describe what your agent does and how it behaves. An agent is a single thing to build, test, and publish: its instructions, the tools and knowledge it can reach, and the branches of behavior it needs.

Most agents start as a single prompt. You add structure only where the conversation needs it, rather than starting from a graph and filling it in.

The examples here build a front desk agent for Northwind Dental, a fictional practice.

## Prerequisites

- A [Bland account](https://v2.app.bland.ai/signup)
- An agent to work in, from **Overview** or from [Build your first agent](/build-your-first-agent)
- For an existing pathway or persona, [Migrate to agents](/platform/migrate-to-agents) first

## Find your way around

Open an agent and choose **Build → Agent**. Select the agent or a node on the canvas to edit it in the configuration inspector on the left. The inspector changes with your selection, including prompts, variables, routing, and settings. Agent-level **Settings** and **Guardrails** are available in the builder navigation.

The canvas shows the agent's flow. Open a pathway or authentication zone to edit its steps. **Test** opens the **Testing** panel beside the canvas so you can test while keeping the flow and inspector visible. The top bar shows autosave status, the environment or branch selector, and publish controls.

## The two prompts

An agent has two prompt fields, in the agent inspector. Their scope determines where the instructions apply.

**Prompt** is the first field. Its description starts "Define this node's goal and instructions." This is what the agent is trying to do and how it should get there: how it opens, what it asks, where it routes.

**System prompt** is directly below it. It sets the agent's personality, tone, and communication style across all pathways. Tone, formality, how much it says at once.

The distinction that matters is **this node** against **every node**. The first applies while the conversation is here. The second applies everywhere, including inside every pathway.

<Note>
  Only the first field supports `@` tagging. The system prompt is agent-wide
  configuration with no node to hang a tool on, so tools and knowledge are
  tagged in the **Prompt** field.
</Note>

## Write the prompt

Both fields are rich text editors. In **Prompt**, describe the agent's goal, the actions it should take, and when it should route into a pathway.

Write in plain language. Describe the job, the order things should happen in, and what the agent should do when the caller goes sideways. You do not need to script exact wording, and agents generally sound better when you do not.

### Tag tools and knowledge with @

Type `@` in the prompt to reference a tool or a knowledge source by name. `@check-calendar` tells the agent this is the moment to check the calendar. The same works for knowledge: `@service-menu` points it at that source.

Two sections below list what the agent currently has:

- **Tool references**, with **Add tool**, **View all tools**, and **Create tool**. Add an existing tool or tag it in the prompt.
- **Knowledge references**, with **View all sources** and **Upload source**. Tag a source or attach it from Knowledge.

Tools are scoped to the prompt or node where they are attached. Knowledge can also be attached to the whole agent.

Creating a tool from the Tools library does not attach it. Creating it from **Tool references** in a prompt also tags it into that prompt. Uploading a source adds it to the library; attach it on Knowledge or tag it in the prompt to make it available.

For tools, attachment is per prompt. Use **Add tool**, **Create tool** in Tool references, or `@` tagging to make a tool available during the conversation at that node. Tagging also attaches a copy rather than a link, which matters every time you edit a tool after tagging it. See [Tag a tool into a prompt](/agents/tools#tag-a-tool-into-a-prompt).

For knowledge, there is a second path. A source can also be attached to the agent from the [Knowledge](/agents/knowledge) page, and an attached source is available whether or not you tag it. Tagging still helps, because it tells the agent where in the conversation you expect the source to matter.

<Warning>
A tool saved only in the library is not available to the agent. Check **Tool references** on the node that should use it, then add or tag the tool there.

An uploaded source still needs attachment. Attach it on the [Knowledge](/agents/knowledge#attach-a-source-to-an-agent) page or tag it in a prompt.

</Warning>

## Extract variables

**Variables to extract** holds key and value pairs the agent pulls out of the conversation and reuses later in the same conversation. A caller's name, a date they asked for, a member number.

The section says so plainly: "Key:value pairs the agent extracts to reuse during the conversation. Adds turn latency."

Take that last part seriously. Every variable is work the agent does mid-conversation, and each one costs a little response time. Extract what you will use. Skip what you will not.

## Extend the agent with pathways

A single prompt handles a surprising amount. When it stops being enough, pathways carry the parts that need their own handling. The section describes them as extending your core agent's skills.

<Note>
  Pathways describe the agent's conversation flow. Simulated callers are [test
  cases](/agents/evaluations), a separate testing feature.
</Note>

Add one with **Add pathway**. The menu offers three kinds to create, plus **Add existing**, which opens **Add an existing pathway**, to reuse one from this agent or another one.

### Prompt

A single prompt for one job, like booking an appointment or handling a cancellation. Think of it as one focused instruction the agent moves into and back out of.

Prompts are also how you manage context. Splitting scheduling out of the main prompt keeps the agent from carrying scheduling instructions through every unrelated conversation.

### Pathway

A flow you lay out yourself: steps you place, and the pathways you draw between them. Open it to edit its steps on the canvas. Custom code and webhook steps are available here.

Choose this when the steps have to happen in a guaranteed order: a scripted disclosure, a verification sequence, anything you need to be able to point at and prove ran the same way every time.

If the canvas gets cluttered, click **Auto layout** in the canvas toolbar. It rearranges every card into a top-to-bottom layout with nothing overlapping. The new layout saves like any other edit, and **Undo** puts the cards back where they were.

### Authentication zone

A gate. It has the steps a pathway has, plus identity questions. On enterprise plans it also offers an SMS code step; on other plans that step is not in the menu.

In the Pathways list, drag other pathways underneath an authentication zone to protect them. A caller then has to get through authentication before the agent will move into anything beneath it. Use it for anything that exposes account details.

### Set the routing condition

Open the pathway and set its **Routing condition** to explain when the conversation should enter it. Review its incoming edges too: the builder supplies default routing text for edges without an explicit label, so an empty condition does not guarantee the pathway is unreachable.

A Prompt opens in a panel, so you stay where you are. A Pathway or an Authentication zone opens into its own canvas, with the routing condition on a panel beside it.

## Configure settings

**Agent → Settings** holds the rest of what is true of the agent rather than of one conversation: display name, voice, language, memory, and metadata.

The tab runs: name, voice and languages, channels, memory, metadata, and request data. Request data is the pair to Variables to extract: facts you hand the agent before the conversation rather than ones it works out during it.

Agent metadata defaults appear in call details and webhooks. Request data is available to the agent as `{{variables}}`. On inbound calls, number metadata and request data override matching agent keys. On outbound calls, per-call `metadata` and `request_data` objects each replace the entire matching default object, including when you pass `{}`. Outbound metadata is also copied into `request_data.metadata` for pathway use.

### Rotate voices across calls

To vary how the agent sounds from call to call, open the **Voice** dropdown and check **Select multiple voices** at the top. Then select up to 20 voices. The closed field lists your picks, such as "Allie, Maya, and Josh".

On every real inbound and outbound call, Bland picks one voice from the list at random. If a voice was deleted or your organization can no longer use it, Bland skips it. If none of the voices are usable, the call uses the first voice you picked.

- Test runs and previews always use the first voice you picked. Only real calls rotate.
- If an outbound call request sets its own `voice`, that voice is used instead of the rotation.
- Uncheck **Select multiple voices** to go back to one voice. The agent keeps your first pick.

<Warning>
A new agent opens with **memory on** and **call recording on**.

Memory writes facts about the person into their contact record. Turning it off later stops further extraction but does not delete what was already written. Recording is under **Advanced settings**, as **Disable recording (PCI compliance)**.

Both are worth a deliberate decision before the agent takes a real call.

</Warning>

With memory on, a memory schema section appears below the toggle, where you define what the agent should remember about a person. The contact records themselves live under **Contacts**, a tab on [Conversations](/agents/conversations).

Advanced settings also cover context management, excluding responses from logs, and image sending.

## Guardrails

Open **Guardrails** in the builder navigation. A guardrail checks a conversation while it runs. Its optional actions are **End the call**, **Transfer the call**, and **Move to a step**. End and transfer describe phone actions. On messaging, the end action ends the conversation; moving to a step changes its route. Phone transfer is not supported on messaging. With no action attached, the violation is recorded and the conversation continues.

Four built-in guardrails cover the standard TCPA disclosures: AI disclosure, recording disclosure, self introduction, and opt out. Each is a switch, and a new agent starts with all four off. The first three also take a window, the number of seconds by which the agent must have said it, defaulting to 30.

Built-in guardrails are available on every plan.

You can also write custom guardrails, which require an enterprise plan.

<Note>
  Guardrails are monitoring. They do not guarantee regulatory compliance, and
  they are not a substitute for your own legal review of how you use the
  product.
</Note>

## Test as you build

Select **Test** above the canvas to open **Testing**.

Testing shares the workspace with the canvas. Open a pathway or authentication zone to edit its nodes and edges while testing.

Testing has two tabs:

- **Manual** is the build loop. Talk to the agent yourself, watch the debug logs as it works, change something, try again. To dig into one answer, open it in [Testbed](/agents/testbed) from the test-tube icon in the chat header or beside the turn.
- **Simulation** generates one conversation for each selected saved test case. Judges are optional. **Create test case** opens the editor in a new tab. That is covered in [Evaluations](/agents/evaluations), where test cases and judges are built.

Test manually while you are shaping behavior. Move to simulation once the behavior is roughly right and you want to know whether a change broke something that used to work.

## Publish and promote

**Publish** saves a version and deploys it. The environment selector shows what you are viewing, starting at **Development**.

For an agent that has never been deployed to Production and has no enabled required checks, the first publish goes directly to **Production**, with Staging pointed at the same version. If required checks are configured, use the staging path instead.

After the first deployment, **Publish** offers:

- **Publish to Staging**: save a new version and run configured checks before pinning it to Staging. Live callers keep the current Production version.
- **Force promote to Production**: send the saved version directly to Production and repoint Staging, bypassing required checks. This puts unchecked changes in front of live callers and records the bypass in the audit log.

To release a staged version normally, use **Promote** on [Environments](/agents/environments). Calls use Production by default, so an agent with no Production version cannot answer them.

Checks can take minutes. The publish dialog closes, and results appear on the Environments **Checks** card. A blocked publish still saves the version on Development without numbering or pinning it to Staging; fix the failures and publish again.

A successful publish switches the builder to the environment it reached. Published environments are read-only; switch to **Development** to keep editing. Publishing from a branch deploys that branch's saved version and leaves the branch open. **Merge** is a separate action.

A promoted agent still needs somewhere to receive conversations. See [Dispatch](/agents/dispatch) for attaching a phone number and choosing channels.

## Common failures

<AccordionGroup>
  <Accordion title="The agent does not answer the phone">
    Check that Production holds a version and the phone number is attached. A publish to Staging leaves Production unchanged; promote that version from [Environments](/agents/environments), then redial.
  </Accordion>

<Accordion title="A pathway never runs">
  Check the routing condition and incoming edges. Give the agent a clear
  condition for entering the pathway.
</Accordion>

<Accordion title="The caller gets stuck partway through">
  Usually a node in a pathway with no exit route. Open the pathway and check
  that every node has somewhere to go.
</Accordion>

<Accordion title="The agent never uses a tool you built">
  Add or tag it on the node that should use it. A tool saved only in the library
  is not available during the conversation.
</Accordion>

  <Accordion title="The agent answers slowly">
    Check how many variables you are extracting. Each one adds latency to the turn it runs on.
  </Accordion>
</AccordionGroup>
