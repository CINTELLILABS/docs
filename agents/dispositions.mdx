A disposition is a standing question you ask of every call an agent takes.

Did the caller book? Which plan did they ask about? Was the agent rude? You write the question once, publish it, and from then on every call the agent handles produces an answer, delivered to the same webhook the call already reports to.

<Note>
Dispositions are an enterprise feature, and they are switched on for enterprise organizations one at a time. The sidebar item is always there, so what you see when you click it tells you which of the two you are:

A greyed row leading to a sales page means the organization is not on an enterprise plan. "Dispositions isn't available here" means you are on enterprise but not switched on yet, and your Bland partner can ask for it.
</Note>

## Prerequisites

- An agent that has taken real calls, from [Agent builder](/agents/agent-builder)
- A post-call webhook already configured, since that is where results arrive
- An owner, admin, operator or prompter role. Anyone else can read dispositions and nothing more

## Where dispositions live

Inside an agent, under Configure. There is no organization-wide view: a disposition belongs to one agent, and you reach it from that agent.

There is also no environment selector on this page. A published disposition runs on every call the agent handles, in every environment.

## What a disposition is made of

A disposition is a set of **values**. Each value is one thing you want to know, and each one names where its answer comes from.

There are four sources, and picking the right one is most of the work:

| Source | Use it when | Where it comes from |
| --- | --- | --- |
| **Org judge** | The answer needs judgement. Was this call handled well? | A published judge from [Evaluations](/agents/evaluations) |
| **Pathway variable** | Your agent already extracts this during the call | An extraction configured on this agent, rerun after the call |
| **Extractor** | You want structured data the agent wasn't already collecting | An extractor you author here |
| **Custom code** | The answer is a calculation, or it has to reach your systems | JavaScript you write |

Two things worth knowing before you choose.

A **pathway variable** is re-extracted, not read back. Dispositions reruns the variable's own frozen prompt against the corrected post-call transcript rather than reusing whatever the agent captured mid-call, so the answer can differ from what you saw live, and usually it is better.

**Custom code always runs last**, after every judge and extractor has finished, and it can take their results as inputs. It cannot take another custom code value as an input.

## Build one

<Steps>
  <Step title="Create the disposition">
    Open Dispositions inside your agent and create one. It is created immediately, with no confirmation step, as a draft named Untitled disposition. Rename it by clicking the title.

    The description field asks "What is this disposition for? Who consumes it?" It is worth answering. Whoever inherits this needs to know which downstream system reads the result.
  </Step>

  <Step title="Add your first value">
    Click **Add value** at the bottom of the Values table. A drawer opens with five cards:

    | Group | Card | What it does |
    | --- | --- | --- |
    | Judges | **Bring in an existing judge** | Picks a published judge. Stays in the drawer |
    | Judges | **Create a new judge** | Leaves for Evaluations, and does not bring you back |
    | Variables | **Rerun a pathway variable** | Picks extractions this agent already runs. Stays in the drawer |
    | Variables | **Create a new variable extraction** | Opens the Extractors manager |
    | Custom code | **Run custom code** | Writes JavaScript. Stays in the drawer |

    The two that leave are worth knowing about before you click. Creating a judge takes you to Evaluations with no route back, so finish the judge and navigate here again. Creating a variable extraction is the only door to extractors anywhere in the product.
  </Step>

  <Step title="Set its logic">
    Every value except custom code gets an **Intelligence** setting: Automatic, Low, Medium or High. It decides how much reasoning the answer is worth paying for, and the drawer shows an estimated cost per call as you change it.

    High is for ambiguous or high-stakes questions. Most values do not need it.
  </Step>

  <Step title="Say what the answer looks like">
    The **Output** section of the value drawer is where you declare the answer's type, so whatever reads your webhook knows what it is getting. A yes or no question wants a boolean, not a sentence saying yes.
  </Step>
</Steps>

You can add several values in one pass when you are picking pathway variables; the button counts them.

## Decide when and how the answer arrives

Three settings on the disposition, not on individual values.

### Delivery Timing

**Immediately on conversation end** delivers within 30 minutes. Use it when something acts on the answer: a webhook, a CRM update, transfer logic.

**Queued** delivers within 24 hours. Use it for reporting, QA and analytics, where nothing is waiting on the result.

<Note>
The screen describes Queued as lower cost. Both settings run the same way on the same models, so what you actually change is the deadline, not the price.
</Note>

### Webhook behavior

**Follow-up event** is the reliable default. Your call webhook fires as usual, and a second event carrying the disposition result follows once it finishes.

**Hold original webhook** waits for the disposition, then sends one combined webhook. It adds up to 30 minutes of latency, and it needs Immediately on conversation end, so choosing it rules Queued out.

### Shape

By default the payload carries every value. Shape is a JSON editor where you write a transformation tree, so the payload matches what your destination already expects rather than making that system adapt. **See example** shows a worked one, and **Save transformation** stays disabled until the JSON parses.

If your destination is happy reading the default, skip this.

## Test it before you publish

**Test** runs the disposition against real calls the agent has already taken, so you can see the answers before anything ships.

<Warning>
A test run bills exactly like a production run. It uses the same models on the same calls and it is metered the same way.

What it does not do is deliver. No webhook is sent for a test run, so nothing downstream sees the results.
</Warning>

The run page shows each call, what each value produced, and the evidence behind it. When an answer is wrong you can correct it, and corrections are kept with the run.

**Align with AI** reads your corrections and proposes changes to the disposition that would have produced them. Applying a proposal to an org judge forks it into an agent-scoped copy, leaving the original judge alone.

## Publish it

Publishing is what turns a disposition on. There is no separate enable step.

It freezes the current draft as an immutable version, and that version is what runs. Later edits become a new draft, and the header shows Unpublished changes until you publish again. Finished runs keep the exact definition they ran under, so editing a disposition can never rewrite history.

You cannot publish a disposition with no values.

## Read the results

Results arrive on your post-call webhook under `agent_dispositions`.

With Follow-up event, the recommended default, they arrive as their own event a little after the call's own webhook:

```json
{
  "event_type": "dispositions",
  "call_id": "c1a9f3d2-64be-4f07-9c5a-2b81e6d0a7f4",
  "agent_dispositions": [
    {
      "disposition_id": "3f2b9c14-8d7e-4a51-b0c6-9e2a7d4f1b83",
      "disposition_version_id": "8c5e1a76-2f40-4db9-a318-6d9b0c4e5721",
      "disposition_key": "booking_outcome",
      "name": "Booking outcome",
      "status": "complete",
      "payload": { "booked": true, "plan": "annual" },
      "values": [
        { "key": "booked", "state": "produced", "value": true },
        { "key": "plan", "state": "produced", "value": "annual" }
      ],
      "executed_at": "2026-09-30T14:22:10.000Z"
    }
  ]
}
```

`payload` is your transformation's output, the shape you asked for in Shape. `values` is the raw list alongside it, and every value carries its own `state`: `produced`, `no_value`, or `error`. That is how you tell a real `null` from a question that could not be answered.

With Hold original webhook, there is no second event. The results ride the call's own webhook instead, under the same `agent_dispositions` field.

Results also appear on the conversation itself, in [Conversations](/agents/conversations).

## Coming from citations and outcomes

Dispositions replace three V1 surfaces: citations, outcomes and reports.

The mapping most people find useful: an outcome was deterministic code, and that is now a custom code value. A citation was an LLM answering a question, and that is now a judge value. Both live in one place instead of two.

Migrating an agent is how you bring the rest across. You start it from **New agent**, then **Migrate**, and [Migrate to agents](/platform/migrate-to-agents) walks through it.

<Warning>
Dispositioning built on node tags does not migrate. If you tagged nodes and read those tags to classify calls, there is no equivalent to move.

The route forward is a custom code value that reads tool names out of the call's execution trace. It is more work than a migration, and it is worth scoping before you commit to a date.
</Warning>

## Common failures

<AccordionGroup>
  <Accordion title="The sidebar item is there but the page says it isn't available">
    Two separate things gate this feature. Being an enterprise organization gets you the sidebar item; a separate rollout decides whether the page loads. You are in the gap between them, and there is nothing to retry. Your Bland partner can ask for the organization to be switched on.
  </Accordion>

  <Accordion title="Some calls produce no disposition at all">
    Four things skip a call, and none of them leaves you an error.

    Three are about the call: redaction applied to it, your organization sits inside a government boundary, or the call has aged past your retention window.

    The fourth is timing. Dispositions get two seconds to start as the call completes, and a call that misses that window finishes without them. It is rare and it is not tied to anything you configured, so if a handful of calls are missing results with no pattern, this is usually why.
  </Accordion>

  <Accordion title="I published, but nothing arrives on my webhook">
    Check which webhook behavior you chose. Follow-up event sends a second, separate event after the call's own webhook, so a listener that only reads the first one never sees it.

    Also check the field name. Results arrive under `agent_dispositions`, not `dispositions`.
  </Accordion>

  <Accordion title="Queued is greyed out">
    You have Hold original webhook selected, which requires immediate timing. Switch the webhook behavior to Follow-up event first.
  </Accordion>

  <Accordion title="I can't find extractors">
    They have one door: Add value, then Variables, then Create a new variable extraction. There is no sidebar item and no direct link. An extractor also has to be published before a value can use it.
  </Accordion>

  <Accordion title="My value returned nothing and I don't know why">
    Open the run and read the evidence for that value. A judge with no inputs enabled cannot answer, and the drawer warns about it at the time.

    Check the value's own `state` rather than the disposition's `status`. A disposition reports `complete` when it finished, which it can do with a value that errored inside it.
  </Accordion>
</AccordionGroup>
