---
title: 'Migrate from V1'
description: 'Where every V1 feature went, what the migration tool moves, and what changes on the way across'
---

Migrating never edits your V1 work. It reads your pathways and personas and writes a new agent beside them. Your pathways keep running, your personas keep answering, and the V1 pages for both stay where they are.

<Warning>
**Migrate with Bland** is the exception worth reading twice. It tests the rebuilt agent by holding real conversations, and those conversations call the tools your pathway already has configured, so they can create bookings, send messages or update records in your own systems.

The product warns you before it starts. Check what your pathway is connected to first.
</Warning>

## Prerequisites

- An owner, admin, operator or prompter role
- A V1 pathway or persona to move

## What the tool actually moves

Two things: **pathways** and **personas**.

Everything else is rebuilt by hand. Dispositions, triggers, phone number settings, test cases and test configurations do not come across, because they are not part of a pathway or a persona.

That is worth knowing before you start, because "migration" sounds like it covers the account.

## Where everything went

### Building

| V1 | V2 | Where |
| --- | --- | --- |
| Pathways | An **agent**, or a **scenario** inside one | Agent, then **Build** |
| Personas | An **agent** | The agent itself |
| Nodes | **Flow steps** inside a complex scenario | Inside the scenario |
| Global prompt, the "golden node" | The agent's system prompt | Agent **Settings** |
| Knowledge bases | **Knowledge** | **Resources** |
| Tools and custom tools | **Tools**, now with tabs | **Resources**, or inside an agent |
| Integrations | **Connections**, a tab under Tools | **Resources** |
| Secrets | A tab under Tools | **Resources** |
| Voices | **Voices**, read-only now | **Resources** |
| Custom code nodes | A `customCode` flow step | Inside a scenario |

There is no Pathways page in V2 and no top-level node graph. A pathway becomes an agent, or a scenario within one, and its nodes become steps inside that scenario. See [Agent builder](/agents/agent-builder).

### Watching

| V1 | V2 | Where |
| --- | --- | --- |
| Call logs, call history | **Conversations** | **Monitor** |
| Transcripts | Inside a conversation | **Monitor** |
| Contacts, memory | A tab under Conversations | **Monitor** |
| Triage | **Issues** | **Monitor** |
| Alerts | **Alerts** | **Monitor** |
| Analytics, reports, boards | **Analytics** | **Monitor**, organization scope |
| Citations and outcomes | **Dispositions** | Agent, **Configure** |

Conversations absorbed three separate V1 log pages. See [Conversations](/agents/conversations).

### Dispatching

| V1 | V2 | Where |
| --- | --- | --- |
| Phone numbers | **Phone numbers** | **Dispatch**, organization scope |
| SIP | A tab under Phone numbers | **Dispatch** |
| Automations | **Triggers** | **Dispatch** |
| Batches | **Batches** | **Dispatch** |
| SMS, messaging | A tab under **Channels** | Agent, **Dispatch** |
| Web widget | A tab under **Channels** | Agent, **Dispatch** |

See [Dispatch](/agents/dispatch), [Triggers](/agents/triggers) and [SIP](/agents/sip).

### Testing and shipping

| V1 | V2 | Where |
| --- | --- | --- |
| Evals, scorecards | **Evaluations**, at `/judges` | **Validate** |
| Scenarios, the V1 test object | Split between test cases and judges | **Validate** |
| Testbed | **Testbed**, from a conversation | **Validate** |

Environments, versions and promotion have no V1 equivalent. See [Environments](/agents/environments).

<Note>
Two words changed meaning rather than moving.

A **scenario** in V1 was a test. In V2 it is a branch of agent behavior, and the V1 test object split into test cases and judges.

A **call** is now a **conversation**, because the same surface carries phone, messaging and web chat.
</Note>

## Run the migration

<Steps>
  <Step title="Open the scope selector and choose New agent">
    Then **Migrate**. This is the only way in. There is an import control inside the builder as well, but it adds to an agent that already exists, so it cannot be your first step.
  </Step>

  <Step title="Pick pathways, or one persona">
    A persona becomes one agent: its prompts, voice and call settings become the agent, each pathway condition becomes a complex scenario, and each skill becomes a simple scenario.
  </Step>

  <Step title="Choose a method">
    **Select your migration** offers three.

    **Import as v2** copies your pathway across as it is, one agent per pathway, with no rewriting and no simulation. It is the fastest and the most predictable.

    **Migrate with Bland** rebuilds the agent from the pathway and checks its behavior against test conversations before handing it over. It runs in the background and takes a while.

    **Migrate with your agent** hands you a prompt to run in your own coding agent, so you watch every step and can steer. See [Migrate a v1 pathway to a v2 agent](/platform/migrate-v1-to-v2).
  </Step>

  <Step title="Finish">
    **Import as v2** ends on **Migrate agent** and cannot be cancelled once it starts, though it is quick. **Migrate with Bland** ends on **Start migration** and can be cancelled while it runs, until it begins finalizing.
  </Step>
</Steps>

<Warning>
**Check what happened to your End Call nodes.**

**Import as v2** keeps them hanging up, but only when every exit from the pathway is an End Call. If some exits end the call and others fall out of a component, the two cannot be told apart, so the whole flow returns to the agent instead of hanging up.

On every other path an End Call node becomes a wrap-up step that hands control back to the agent.

Either way the migration says so and continues. If a pathway relied on ending calls at a particular point, add an End call node at the agent level.
</Warning>

Warnings do not appear in the modal. You get a toast saying how many items are flagged, and then a banner over the builder canvas naming the pathway and the count, which you can dismiss.

Three smaller things are dropped, each reported as a warning: a pathway's own global prompt when you migrate a persona, exit pointers on fanned-out components, and tool overrides on a persona's skills.

## Do it twice and you get two agents

The migration has no memory of having run. Running it again on the same pathway produces a second agent rather than updating the first.

That is safe, since nothing is overwritten, but it does mean a hesitant second attempt leaves you tidying up.

## Common failures

<AccordionGroup>
  <Accordion title="My pathway looks nothing like it did">
    You used a method that rebuilds rather than copies. **Import as v2** is the one that copies step for step. Run it again with that method and delete the agent you do not want.

    The same split exists inside the builder: **Import pathways** there has a **Migrate with AI** switch on each row, on by default, and turning it off copies the pathway as it is.
  </Accordion>

  <Accordion title="The agent will not hang up">
    Your End Call nodes became wrap-up steps. That happens on every method except **Import as v2**, and on that one too if the pathway mixes End Call exits with component exits. Add an End call node at the agent level.
  </Accordion>

  <Accordion title="I cannot find Import pathways">
    It is inside an agent, not on the agent list, because it imports into an agent that already exists. To start from nothing, use **New agent** then **Migrate**.
  </Accordion>

  <Accordion title="My dispositions and triggers did not come across">
    They were never in scope. The tool moves pathways and personas only; everything else is rebuilt.
  </Accordion>

  <Accordion title="My V1 pathway disappeared">
    It did not. The migration never writes to V1, and the V1 pathways and personas pages are still there. Check you are not looking at the V2 agent list expecting to see it.
  </Accordion>
</AccordionGroup>
